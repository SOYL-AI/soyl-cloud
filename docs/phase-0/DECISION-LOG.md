## M1

- 2026-07-27 · M1 · **Neither database role has `BYPASSRLS`, contradicting the handbook §48.7** — granting `BYPASSRLS` requires superuser, which managed providers generally do not give out, so requiring it for `soyl_migrator` would have made migration 001 unportable to Neon and Supabase. A migration that must touch tenant rows toggles `FORCE` off inside its own transaction instead, which the table owner may do unaided.
- 2026-07-27 · M1 · **`core.membership_property` gains a `tenant_id` that `UPDATE.md` §7 does not specify** — with only the two foreign keys it is the one tenant-scoped table RLS cannot protect directly, and the schema-wide assertion would have had to special-case it. Reachability through `core.membership` is not the same guarantee as a policy.
- 2026-07-27 · M1 · **`core.user_account` is deliberately not tenant-scoped and has no RLS** — a user may hold memberships in several tenants, and login must resolve a user by email before any tenant is known. Tenancy lives on `core.membership`. Recorded as a named exception in the isolation suite so it cannot be mistaken for an oversight.
- 2026-07-27 · M1 · **`core.tenant`'s policy keys on `id`, not `tenant_id`** — the tenant *is* the row. A side effect worth knowing before M2: a tenant row can only be inserted by a session already scoped to its own id, so signup must generate the UUID first and set the context before writing.
- 2026-07-27 · M1 · **Policies carry `WITH CHECK` as well as `USING`** — `USING` alone filters reads and still permits inserting a row stamped with another tenant's id: invisible to them afterwards, but present, and counted in their exports and their bill.
- 2026-07-27 · M1 · **Migration and admin credentials live in `.env.migrations`, not `.env`** — `Settings` uses `extra="forbid"`, which caught the API process being handed the migrator credential through a shared file. The separation is now enforced by the same rule rather than by intention.
- 2026-07-27 · M1 · **Leads are written by calling the API, not by adding a Postgres driver to the web app** — keeps the RLS-role story in one place and avoids a serverless function opening connections to Postgres per submission. Costs a shared bearer token until M2's JWT exchange.
- 2026-07-27 · M1 · **Compose publishes Postgres on 5433 and Redis on 6380** — a developer machine with Postgres installed already owns 5432, and on Windows the published port binds without error while connections still reach the native service. It presents as `password authentication failed for user soyl_migrator`.
- 2026-07-27 · M1 · **Railway's healthcheck points at `/live`, not `/health`** — Railway restarts a container that fails its healthcheck, so checking Postgres there converts a database blip into a restart loop.
- 2026-07-27 · M1 · **Lint stays non-blocking while typecheck becomes blocking** — the 15 lint errors are pre-existing and mostly accessibility-related, which is M5's work. Typecheck was at 1 and is now 0, so blocking it costs nothing today and prevents the debt returning.

## M3

- 2026-07-28 · M3 · **Building M3 before the legal review, with an explicit boundary** — `DECISIONS.md` §6 makes the lawyer a hard gate on M3. The founder has chosen to proceed and audit later. The gate is read as binding on *a hotel uploading its documents*, not on the pipeline existing: M3 is built and tested against our own documents, and **no pilot hotel uploads anything until the DPA is signed**. That line is the whole of the deviation; if it moves, the deviation becomes the thing §6 actually forbids.
- 2026-07-28 · M3 · **Two DPDP-relevant designs are being brought forward rather than retrofitted** — real erasure (documents, chunks and embeddings, not just `deleted_at`) and PII minimisation before inference (`UPDATE.md` §6.8). Both are cheap now and expensive after a corpus exists, and both are what a processor DPA will be audited against.
- 2026-07-28 · M3 · **Azure abuse monitoring stays ON, deliberately, until we have a replacement guardrail** — `DECISIONS.md` §6 asks for zero retention, and disabling abuse monitoring is how Azure grants it. But abuse monitoring *is* a safety control: turning it off removes the only thing currently watching for misuse of the model, and we have nothing standing in its place. Founder's call to keep it and revisit once input guardrails exist (handbook §38.2 fencing, §58.5 PII minimisation). **Consequence for the DPA:** Microsoft retains prompts and completions for up to 30 days for abuse review, which is a sub-processor disclosure a pilot hotel's counsel will ask about. It is disclosable, not disqualifying — but it must appear in the DPA rather than be discovered.
- 2026-07-28 · M3 · **PII minimisation (`UPDATE.md` §6.8) becomes higher priority because of the above** — with retention on, whatever reaches the model is held for 30 days. Stripping guest names, emails and phone numbers *before* inference therefore shrinks the retained surface as well as the inference surface, which makes it the natural first guardrail to build when we revisit this.
- 2026-07-28 · M3 · **Local service URLs use `127.0.0.1`, never `localhost`** — on Windows `localhost` resolves to IPv6 `::1` first, where a stale `wslrelay` can be listening alongside Docker's own `::` binding. The relay accepts the connection and forwards nowhere, so the client connects and then times out on the protocol handshake while `docker compose ps`, `pg_isready` inside the container and a raw socket connect all report success. Second time a Windows port subtlety has cost an hour on this project, after the 5432 collision in M1; both are now in `SETUP.md`.


## M4

- 2026-07-29 · M4 · **Reranking is the LLM listwise fallback, not the cross-encoder §45.3 prefers** — the handbook wants Cohere Rerank or an Azure-hosted cross-encoder, and names an LLM listwise rerank as the fallback "if reranking is unavailable". It is unavailable: our Azure AI Foundry resource has an embedding deployment and a chat deployment, and no cross-encoder. Built behind `RerankProvider` so swapping one in later is a factory change, and the fake is used in CI. **Consequence:** precision@5 measured today is a floor, not the number §45.3 projects.
- 2026-07-29 · M4 · **The rerank latency budget is 12s, not §45.3's 400ms** — 400ms is a cross-encoder number, one forward pass over 30 short pairs. An LLM scoring 30 candidates takes seconds. Holding the fallback to 400ms would time it out on every request and leave a reranker that looked alive and never ran. It is a circuit breaker against a hung provider, not a latency target; the target returns to 400ms with a real cross-encoder.
- 2026-07-29 · M4 · **The reranker asks for scores, not an ordering** — a permutation invites dropped and repeated candidates, and one garbled entry costs the whole list. Independent per-candidate scores mean a bad entry costs that candidate, the sort is ours and therefore deterministic, and unscored candidates fall back to fusion order rather than vanishing.
- 2026-07-29 · M4 · **A reranker that fails costs quality, never the answer** — timeout and provider errors fall back to fusion order with `reranked=False` and a reason. "Never configured" and "failed today" are deliberately distinguishable in the result: both give fusion order, only one is worth waking up for.
- 2026-07-29 · M4 · **`redis_settings` moved out of the worker module** — the upload route needed a Redis DSN and imported it from `worker`, which pulled the ingestion pipeline, the provider factory and the OpenAI SDK into the API process. `import-linter` caught it as a §6.9 violation along a four-hop chain: the direct import was innocent, the transitive consequence was not.
- 2026-07-29 · M4 · **The labelled retrieval set is synthetic, and is a development set rather than acceptance evidence** — `UPDATE.md` §M4 asks for 40 pairs "built from real pilot documents". There are none, because the M3 boundary holds until the DPA is signed. Seven realistic hotel documents were written instead, then questions written in operator voice from a topic list without reusing the documents' phrasing, which is the only part of the circularity that can be mitigated. It caught three real bugs; it is not independent evidence. Replace or extend with real documents when the DPA lands.
- 2026-07-29 · M4 · **`precision@5` as §M4 specifies it is not measurable against single-answer questions** — standard precision@5 caps at 0.2 when one chunk is correct, so the 0.70 target would be unreachable. Ours divides by the number of relevant chunks, which makes the target meaningful but reduces the metric to "was the answer in the top 5" — recall by another name. `context purity` (relevant ÷ returned) was added as the honest dilution measure §45.3 actually argues from, and it is the one that is not saturated: 0.750 against 1.000 for the headline pair.
- 2026-07-29 · M4 · **A perfect recall score is being read as a signal that the set is too easy** — 50 chunks means top-10 is a fifth of the corpus, and the near-miss traps were designed by the person who knew they were traps. The number is not being reported as M4 acceptance met.
- 2026-07-29 · M4 · **The eval paces itself and retries rather than letting a rate limit degrade it silently** — reranking that is rate limited falls back to fusion order by design, which on the request path is correct and in a measurement is invalid. One run reranked 25 of 40 questions and still printed a full report. The provider keeps `max_retries=0`; the pacing lives in the harness, where nobody is waiting.
- 2026-07-29 · M4 · **`understand` is not a pipeline stage in Phase 0** — §9 lists it, but there is nothing to resolve: the tenant comes from the session, property scope from the membership, and there are no dates or metrics to parse because there are no metrics. It would be a model call that costs latency and money to restate its input. `Intent` is already on the envelope, so adding it later is additive.
- 2026-07-29 · M4 · **The refusal is written in code, not asked of a model** — spending a synthesis call to phrase "I don't know" makes the cheapest outcome cost the same as the most expensive one, and hands the model an opportunity to answer anyway from context we already judged insufficient.
- 2026-07-29 · M4 · **`alert.callout` is exempt from the provenance requirement** — it carries the pipeline's own voice ("no document covers this"), which is a statement about our corpus rather than a claim drawn from it. Requiring a citation would strip exactly the message whose content is that there are no chunks to cite.
- 2026-07-29 · M4 · **Turn status follows the evidence, not the surviving block count** — a refusal *is* a block, and alerts survive validation by design, so deriving status from block count reported every refusal as a complete answer. Caught by the integration test; status is the one field that must never be wrong, since the eval, the roadmap query and the UI all read it.
- 2026-07-29 · M4 · **The headline is replaced when nothing grounded survives** — `summary.headline` carries no provenance refs, so stripping every block still left the model's assertion in the most prominent field in the envelope. An integration test stripped a fabricated citation correctly and left "cancel free up to 24 hours" against a corpus that says 48. Honest limit: a *partly* stripped answer can still carry a headline summarising a removed block; `degraded` records it, and detecting it properly needs semantic checking.
- 2026-07-29 · M4 · **The public Hotel Advisor cannot be RAG** — founder's product direction is a landing-page chat that qualifies a visitor and shows insight before signup. An anonymous visitor has no tenant and no corpus, so there is nothing to retrieve or cite, and citing a corpus we wrote ourselves would fabricate authority in the one place it does most damage. It is built as a structured diagnostic grounded in the visitor's own answers, with "ask your own documents" as the upgrade.
- 2026-07-29 · M4 · **Streaming emits stages, not tokens** — Phase 0's synthesiser is one structured-output call producing a whole envelope, so there is no partial envelope to send; half-parsed JSON is not a renderable answer. Streaming characters would mean the client either buffers them anyway or renders content the provenance validator has not seen, and that validator is the reason any of it is trustworthy. §9's event names are used, so token streaming later is additive.
- 2026-07-29 · M4 · **An answer that cites nothing is recorded as a refusal, not a completed turn** — found by the end-to-end eval and it was a product bug rather than a measurement one. When retrieval returns weakly related chunks and the synthesiser correctly says "the documents do not cover this", `had_evidence` is true and the refusal is an alert (exempt from provenance), so it survived validation and the turn was written `complete`. §6.5's roadmap query — "what did people ask that we could not answer" — therefore missed every synthesiser-level refusal, which is the subset most worth reading because the corpus nearly covered them.
- 2026-07-29 · M4 · **Conversation history is tenant-scoped, not user-scoped** — a duty manager asks on the late shift and the general manager reads it next morning; in a hotel that hand-off is the normal case. Stored envelopes are returned verbatim and never re-validated on read: re-running the validator against a corpus that changed since would strip a citation that was correct when made, turning a document deletion into a rewritten history.
- 2026-07-29 · M4 · **Sample documents load through the ordinary upload path** — a seeding endpoint would exercise a pipeline we do not ship, and the first question after a sample behaves oddly is whether a real document would too. Labelled as fictional in the UI, because a demo corpus presented as real hotel policy is the dishonesty the advisor exists to avoid.

## M5

- 2026-07-29 · M5 · **The Calendly embed loads on click, not on arrival** — `/book-demo` pulled 3.77 MB of third-party JavaScript before anyone could book, paid for by every visitor who read the page and left. Perf 57 → 95, best practices 77 → 100, LCP 16.8s → 2.6s. The destination is unchanged; the booking flow is still verified after every deploy.
- 2026-07-29 · M5 · **The hero heading is deliberately not animated** — an opacity transition on the LCP element delays LCP by exactly the transition's duration, because the metric measures when the element reaches its *final* painted state. Above the fold, the fastest animation is none.
- 2026-07-29 · M5 · **Both animation libraries are gone from marketing routes** — GSAP was one counter; framer-motion was ~50 KB plus hydration on every route to fade divs in. `IntersectionObserver` and CSS transitions do the same job off the main thread, and this is what actually moved the scores (TBT 350ms → 60–120ms locally). framer-motion still ships on `/app` and `/advisor`, which sit behind interaction.
- 2026-07-29 · M5 · **Marketing pages are RSC via a `Reveal` wrapper** — children passed from a server component to a client component stay server-rendered, so a page keeps its markup out of the bundle while still animating. That property is the whole reason the pattern works and is not obvious from the API.
- 2026-07-29 · M5 · **Lighthouse gates SEO, a11y, best practices, CLS and TBT as errors; performance and LCP as warnings** — the first five pass today. Erroring on the latter two would fail every PR for debt that predates it, which is the reasoning `DECISIONS.md` §5 applied to lint in M0. They must become errors before M5 is signed off.
- 2026-07-29 · M5 · **Routes must be warmed before Lighthouse measures them** — `next start` compiles a route lazily on first request even from a production build. Measuring cold was worth ~13 points of variance and made two measurement rounds invalid before it was noticed. Documented in `BASELINE.md`.
- 2026-07-29 · M5 · **`/resources` is separate from `/blog`** — blog is product and category writing; resources are operational reference, written to be useful without mentioning us. §10 is explicit that bulk content "does not work and it damages a young domain", so the bar each article had to clear was whether a general manager would bookmark it.

## M6

- 2026-08-02 · M6 · **Staff read across tenants through an additive `staff_read` policy, not `BYPASSRLS`** — §11's questions, funnel and cost screens are cross-tenant aggregates by definition, and every table they read is under ENABLE + FORCE RLS keyed on one `app.tenant_id`. A role with `BYPASSRLS` would work and would move the enforcement point out of Postgres into "the admin query remembered to filter", which is exactly the retrofit §6.1 exists to prevent. Postgres OR's permissive policies, so a second `FOR SELECT` policy widens reads without touching `tenant_isolation`, and writes stay governed by it alone.
- 2026-08-02 · M6 · **The staff predicate is a table lookup, not a session variable** — `core.is_staff()` resolves `app.staff_id` against `core.staff_user`, so an arbitrary uuid in the setting reads exactly as much as no setting at all. A predicate of `current_setting(...) IS NOT NULL` would have made cross-tenant access a variable anyone who could reach `set_config` could assert. Revocation is a single `revoked_at` write and takes effect on the next statement, with no claims cache to wait out.
- 2026-08-02 · M6 · **`soyl_app` cannot promote anyone to staff** — the grant is `SELECT` only, so promotion runs through `scripts/grant_staff.py` as `soyl_migrator`. It means no bug in the API can create a staff member, which is the property that makes everything else here worth having. There is deliberately no admin screen for it.
- 2026-08-02 · M6 · **`core.staff_user` is the one table with ENABLE and no FORCE** — under FORCE, its only policy is `FOR SELECT`, so *no* role can insert, including the migrator, and `grant_staff.py` fails with a policy violation. The first version of migration 007 did exactly that and the isolation suite caught it on the fixture that seeds a staff member. The table is not tenant-scoped and the owner is precisely the role that must be able to write it; `soyl_app` is still bounded by the policy for reads and by the missing grant for writes.
- 2026-08-02 · M6 · **`staff_read` policies are created from `pg_policies`, and a test keeps the two sets equal** — a hand-written list in the migration cannot miss a table that exists today and cannot catch one added in 008. `test_every_tenant_scoped_table_has_a_staff_policy` asserts equality in both directions; a table with `tenant_isolation` and no `staff_read` is an admin screen quietly missing a section, and the reverse is something widened that was never narrowed.
- 2026-08-02 · M6 · **`StaffPrincipal` is a separate type from `Principal`, not a flag on it** — `Principal.tenant_id` is a `UUID` every tenant-scoped query is entitled to assume is set. A staff reader has no tenant, and modelling that as `UUID | None` would push a null check into every call site that currently cannot be wrong. The types also mean no admin route can be reached with a tenant principal and vice versa.
- 2026-08-02 · M6 · **A non-staff caller gets 404 from `/v1/admin`, not 403** — 403 confirms the panel exists to someone who was guessing. The refusal is still audited, and the refused rows are the ones worth having.
- 2026-08-02 · M6 · **Impersonation is a session row with `impersonated_by`, read-only by scope, 30 minutes** — a column on `core.session` rather than a parallel table, because an impersonated session must expire, be revocable and resolve to a principal exactly like any other and that table already does all three. Read-only is applied in `PrincipalResolver` via `Principal.read_only()` so no route has to remember; the tenant boundary is RLS regardless. An impersonated session cannot reach `/v1/admin`, so it cannot mint a further impersonation with no trail back to who started it. The account impersonated is chosen deterministically (longest-standing owner) so two people reproducing a report see the same data.
- 2026-08-02 · M6 · **The impersonated token replaces `sessionToken` in `readSession` by default** — every `/app` page and every route handler under `/api` already reads that one function, so the workspace shows the customer's data with no change to any of them and none can be *forgotten*. `/admin` opts out with `ignoreImpersonation`; the API refuses an impersonated session on `/v1/admin` anyway, so getting the flag wrong fails closed.
- 2026-08-02 · M6 · **The questions list is stemmed full text, not `ILIKE '%…%'`** — searching `cancel` finds "cancelled" and "cancellation", which is what someone hunting a theme means, and `websearch_to_tsquery` gives quoted phrases and `-exclusions` without a parser. The cost is no substring-inside-a-word matching. Indexed in migration 007 rather than scanned.
- 2026-08-02 · M6 · **`ai.envelope` now stores the pre-validation draft and the strips** — §11 requires the inspector to show "the raw model output, what validation stripped". M4 logged both at WARNING and persisted neither, so the evidence for the only question the inspector exists to answer expired with the log retention. On the envelope rather than the turn because both are read exactly as often: never, until someone opens one turn.
- 2026-08-02 · M6 · **`billing.usage_ledger` was recording tokens and no money, and now records both** — the answer pipeline omitted `cost_inr` from its INSERT, so the column took its default of zero on every row written since M4. Ingestion had it right; nothing compared the two. `AzureOpenAIRerank` and `AzureOpenAIAdvisor` also took prices in their constructors and had no way to apply them. Pricing is now one shared function, each adapter fills `Usage.cost_inr` for its own call, and `test_pricing.py` walks every adapter and fails if one holds a price it cannot use. §11's cost screen is what needed the number, a milestone and a half after the bug.
- 2026-08-02 · M6 · **The marketing navbar and footer no longer render on `/app` and `/admin`** — both segments bring a complete frame of their own and were sitting underneath a fixed marketing nav with a "Book Demo" button, visible on production `/app` today. Two root layouts is the structurally correct fix and would mean moving every route into a `(site)` group, a large change on the only lead channel we have; reading the path from a header in the root layout would call `headers()` there and make every marketing page dynamic, undoing M5. `SiteChrome` is a client component whose `usePathname` resolves during the server render, so it costs no dynamic rendering and produces no flash. Auth pages keep the chrome on purpose.
- 2026-08-02 · M6 · **The CI lint step now fails when eslint cannot start** — a blanket `brace-expansion@^5` override (added for a ReDoS advisory) broke `require('brace-expansion')` in eslint's `minimatch@3`, so eslint crashed on startup and the step reported "no problems reported" for some time. A missing summary line read identically to a clean run. The override is now scoped to `minimatch@3`, and exit code ≥ 2 is a build failure rather than a quiet one.

## Post-M6 · Marketing Advisor Redesign

- 2026-08-08 · Post-M6 · **Public advisor redesigned from 5-question wizard to multi-turn agentic conversation** — founder directed a shift from fixed questions to adaptive AI profiling. The old endpoint (`POST /v1/advisor`) is preserved for backward compatibility; the new one (`POST /v1/advisor/chat`) accepts full conversation history per turn so conversation state lives on the client, not in Redis.

Embedding it would add chunking, vector search and a marketing tenant for zero retrieval benefit, and would blur the provenance boundary the product depends on.
- 2026-08-08 · Post-M6 · **Figure stripping relaxed for the conversational advisor** — the original `strip_invented_figures` is preserved for the one-shot advisor. The new `strip_visitor_specific_figures` only targets claims about the visitor's specific property, allowing general industry references and product feature claims.
- 2026-08-08 · Post-M6 · **Email capture removed from the advisor gate** — founder directive. The advisor delivers the full insight freely with a natural CTA after. Lead quality over volume.
